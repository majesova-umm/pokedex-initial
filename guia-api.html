    Entiendes qué pasa cuando tu página “le pide” los Pokémon a PokéAPI, y lo ves con tus propios ojos en el navegador.

    Una API es la forma en que dos programas se comunican. Uno, el cliente, hace una petición. El otro, el servidor, responde. En tu Pokédex el cliente es el navegador y el servidor era PokéAPI:

    Navegador (cliente) PokéAPI (servidor) │ │ │ ── GET /api/v2/pokemon/25 ──────▶ │ │ │ busca a Pikachu │ ◀───────── 200 OK + JSON ──────── │ │ │

    REST es un conjunto de reglas para diseñar APIs que usan HTTP, el mismo protocolo de las páginas web. Las ideas principales son cuatro:

    • Recursos con URL. Cada “cosa” tiene su dirección. /pokemon es la colección completa y /pokemon/25 es un Pokémon en particular.
    • Métodos HTTP. El método dice qué quieres hacer con el recurso.
    • Códigos de estado. Cada respuesta trae un número que dice cómo le fue a la petición.
    • JSON. Los datos viajan como texto en formato JSON, que se parece mucho a un objeto de JavaScript.

    Los métodos HTTP

    MétodoPara qué sirveEjemplo en tu API
    GETLeer datosGET /api/pokemon → lista de Pokémon
    GETLeer un solo elementoGET /api/pokemon/25 → Pikachu
    POSTCrear un elemento nuevoPOST /api/pokemon → agrega un Pokémon
    PUT / PATCHModificar un elementoPATCH /api/pokemon/25 → cambia a Pikachu
    DELETEBorrar un elementoDELETE /api/pokemon/25 → borra a Pikachu

    Los códigos de estado que vas a usar

    CódigoSignificaCuándo lo regresas
    200 OKTodo bienUn GET que encontró lo que pediste
    201 CreatedSe creó algo nuevoUn POST que funcionó
    400 Bad RequestLa petición está malFaltan datos obligatorios
    404 Not FoundNo existePiden un Pokémon que no tienes
    500 Server ErrorFalló el servidorUn error en tu código

    Truco para recordarlos: los 2xx son éxito, los 4xx son culpa del cliente y los 5xx son culpa del servidor.

    Un endpoint es una URL de tu API que responde a un método HTTP. En Next.js se crean con un archivo especial llamado route.js. Igual que con page.js, la carpeta donde lo pongas define la URL.

    1. Dentro de app crea una carpeta api, y dentro de ella otra carpeta pokemon.

    app/ api/ pokemon/ route.js ← nuevo, responde en /api/pokemon

    ¿Qué está pasando?

    • El nombre de la función es el método HTTP que atiende. Como se llama GET, Next.js la ejecuta cada vez que alguien hace un GET a /api/pokemon.
    • Response.json(...) convierte el objeto a texto JSON y lo envía como respuesta. Si no indicas un código de estado, por defecto es 200.
    • La respuesta tiene la misma forma que la de PokéAPI: un objeto con count y results. Así tu página va a necesitar muy pocos cambios.
    • @/ es un atajo que significa “la raíz del proyecto”. @/data/pokemons es el archivo que creaste en el paso anterior.

    Tu endpoint filtra resultados con /api/pokemon?search=char.

    Lo que va después del ? en una URL se llama query string, y sirve para mandar opciones a la API. Ya lo usaste sin darte cuenta: en pokemon?limit=150 le decías a PokéAPI cuántos Pokémon querías.

    Reemplaza la función GET de app/api/pokemon/route.js:

    • Ahora GET recibe request, que trae toda la información de la petición: la URL, los encabezados, el cuerpo.
    • request.nextUrl.searchParams.get("search") lee el valor de search en la URL. Si no viene, regresa null, y ?? "" lo cambia por texto vacío. Un texto vacío está incluido en cualquier nombre, así que sin search regresa todos.
    • Escribir results solo es lo mismo que escribir results: results.

    Prueba estas URLs:

    • localhost:3000/api/pokemon?search=char → count: 3
    • localhost:3000/api/pokemon?search=saur → count: 3
    • localhost:3000/api/pokemon?search=xyz → count: 0 y results vacío

    Fíjate que buscar algo que no existe no es un error: la respuesta sigue siendo 200 con una lista vacía. Una búsqueda sin resultados es una respuesta válida.

    /api/pokemon/25 regresa a Pikachu, y /api/pokemon/999 responde con un error 404.

    En REST, cada elemento tiene su propia URL: la de la colección más su id. Como no vamos a crear una carpeta por cada Pokémon, usamos una ruta dinámica: una carpeta con el nombre entre corchetes.

    1. Dentro de app/api/pokemon crea una carpeta llamada [id], con todo y corchetes.
    2. Dentro, crea otro archivo route.js:
    app/ api/ pokemon/ [id]/ route.js ← nuevo, responde en /api/pokemon/1, /api/pokemon/25… route.js

    ¿Qué está pasando?

    • Los corchetes en [id] le dicen a Next.js que esa parte de la URL es variable. Lo que venga en su lugar llega en params.id.
    • params es una promesa, por eso lleva await. Es igual a lo que hiciste con searchParams en el detalle de la ADA8.
    • Todo lo que viene en una URL es texto. Number(id) convierte "25" en 25 para poder compararlo con el id de los datos.
    • .find() regresa el primer elemento que cumple la condición, o undefined si ninguno la cumple.
    • Si no lo encuentra, respondemos con { status: 404 }. El segundo parámetro de Response.json es donde se indica el código de estado.
    1. Abre localhost:3000/api/pokemon/25: debe aparecer Pikachu.
    2. Abre la pestaña Network de las herramientas de desarrollador y luego abre localhost:3000/api/pokemon/999. Verás tu mensaje de error, y en Network la petición aparece en rojo con Status 404.

    Un error bien hecho tiene dos partes: el código (404), para que los programas sepan qué pasó, y un mensaje, para que las personas lo entiendan.
